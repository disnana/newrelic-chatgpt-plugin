# Write and destructive operation approval design

Status: production design plus a synthetic, in-memory rehearsal. The production app has no approval database, approval endpoint, write dispatch, or live New Relic mutation path. Write and destructive tools remain blocked. Do not infer approval from OAuth scopes, tool descriptions, an upstream `readOnlyHint`, a billing opt-in, a tool policy entry, or a prior approval for another call.

## Synthetic rehearsal

`examples/operation-approval/demo.html` is a static, browser-only illustration using fixed fake account/condition IDs. `rehearsal.mjs` has no provider, Worker, D1, credential, or dispatch dependency; its in-memory store is intentionally unsuitable for production. The demo asks the user to enable the rehearsal, displays a fixed effect summary, simulates a one-time approval and claim, and can simulate an `outcome_unknown` stop. The approval nonce stays in local page memory and is omitted by the model/tool-safe serializer. The page uses `textContent` for rendered data and makes no outbound API or provider requests; serve the files over loopback for browser module loading.

`scripts/test-operation-approval.mjs` exercises the mock state machine, owner/session binding, same-origin and CSRF conditions, expiry, cancellation, argument/schema/policy/context drift, replay and concurrent claims, and unknown-outcome no-retry behavior. `scripts/test-operation-approval-ui.mjs` uses a small DOM stub to cover repeated clicks, disabling during creation, stale proposals, exact effect display, and the no-retry UI. The tests also confirm that the real MCP catalog still rejects write policies, the raw transport rejects before `fetch`, and no approval route, write tool, or rehearsal code was added to the Worker bundle. These tests do not validate browser authentication, durable atomic storage, a real session-bound nonce, provider resource ownership, actual effects/costs, or live provider behavior. The production connection page explicitly states that write and destructive operations are unavailable.

## Required flow before any future mutation support

1. **Build a proposal, not an action.** After authenticating the current owner, resolve the exact tool name, full existing tool fingerprint (input/output schema, annotations and metadata), canonical arguments, New Relic account and region, connection generation, operation class, and known billing class. Reject unknown or changed definitions and unknown billing classifications. Verify ownership of exact resource targets; an account argument alone does not prove ownership of arbitrary GUIDs or organization-level resources. Display exact effects in local UI; never use provider-supplied prose as authority.
2. **Get deliberate owner approval.** Authentication by a Sites identity header or signed-proxy JWT identifies a principal but does not prove human approval. Require a deliberate authenticated `POST` with strict JSON content type and a single-use server nonce bound to the browser session, owner, and immutable proposal. Never expose the nonce through MCP or accept an `approved: true` MCP argument. Bind approval to the same subject, account, region, connection generation, operation, canonical-argument hash, full tool/policy fingerprint, and proposal expiry. Protect the browser flow with strict Origin checks and gateway session CSRF protections. A confirmation in chat is not automatically a server-side approval token.
3. **Claim atomically.** Store an immutable, expiring proposal and perform a conditional `pending -> claimed` transition before dispatch. The claim must succeed once only. Revalidate user, account, connection generation, tool policy, current full tool fingerprint, arguments, billing classification, and feature flags at claim time. Account switch, disconnect, reconnect, or credential-principal change invalidates pending approval.
4. **Dispatch once.** Use only the exact reviewed transport path and exact arguments. If using `withNewRelicSession()`, explicitly pass `{readOnly:false}` because its default can replay a callback after refreshable auth failure. Do not expose a raw-tool escape hatch or retry a mutation after `401`, timeout, disconnect, or ambiguous response. Malformed results, a crash or a failure to persist the result after dispatch are `outcome_unknown`; stop and require an operator to inspect provider state. Do not assume the provider supports idempotency keys. Disconnect can fence stale, not-yet-dispatched work but cannot undo an action already sent upstream.
5. **Record safely.** Record proposal ID, subject/account references, tool name, schema and argument hashes, approval/claim timestamps, result class, and correlation IDs. Avoid retaining raw telemetry, full arguments, OAuth data, or bearer assertions in logs. Render provider text and arguments as text, never HTML.

## Independent safeguards

- Every write/destructive tool is disabled by default and requires an explicit operation-specific policy plus a separate approval feature flag. A billing opt-in is not a write approval.
- The UI must show whether an operation can alter alerts, thresholds, routing, entities, or other production state, and must identify any provider costs or external side effects that are known. Unknown effects block the action.
- Authorization must remain owner-scoped; another user cannot view, approve, replay, or alter the proposal. Tests must cover duplicate clicks, stale approvals, changed arguments/schema/policy, cross-origin requests, account switching, disconnect races, concurrent dispatch, and provider timeouts.
- Before release, obtain independent review and test against a dedicated non-production New Relic account with harmless fixtures. Do not use live production entities as approval-flow test targets.

Until the full flow and reviews exist, the implementation's fail-closed write/destructive behavior is the required outcome. This document does not authorize implementation, a live call, production configuration, deployment, or release.
