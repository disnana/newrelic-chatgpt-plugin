# Write and destructive operation approval design

Status: a D1-backed, owner/session-bound approval foundation plus a synthetic, in-memory rehearsal. The foundation supports session bootstrap, proposal listing, one-time challenge issuance, atomic approval/cancellation, and an internal single-use claim state transition. It does not ship any reviewed New Relic write/destructive policy, public proposal-creation route, MCP write tool, or provider dispatch path. The production flag `NEW_RELIC_OPERATION_APPROVALS_ENABLED` defaults to `false`; no approval UI is wired to create a real proposal. Write and destructive tools remain blocked. Do not infer approval from OAuth scopes, tool descriptions, an upstream `readOnlyHint`, a billing opt-in, a tool policy entry, or a prior approval for another call.

## D1-backed foundation (no provider dispatch)

Migration `0004_operation_approval_store.sql` is additive. Existing connections and account preferences remain intact; each row receives an opaque generation, and reconnect/account changes rotate it. The Worker stores only hashes of Site approval cookies, CSRF tokens, gateway session bindings, and one-time approval nonces. Proposal arguments are encrypted at rest; the UI-facing summary is generated by a static reviewed policy, not provider text. Approval uses a single conditional `pending -> approved` SQL update that consumes the nonce. A second conditional `approved -> claimed` update rechecks the owner, active browser session, account/region, connection/account-selection generations, schema/policy/argument fingerprints, expiry and billing class. A claimed action that cannot be safely reconciled transitions to `outcome_unknown`; no retry path exists.

Site mode uses a random `__Host-nr-approval` cookie with `Secure`, `HttpOnly`, `SameSite=Strict`, and `Path=/`, independent of the platform identity header. Every approval request revalidates the current Site owner and requires exact same-origin JSON requests plus a per-session CSRF token. Signed-proxy mode requires a trusted gateway-signed `channel=browser` and stable `sid` claim; `channel=mcp`, missing `sid`, and subject-only assertions cannot bootstrap or approve. The reference gateway keeps the browser cookie at the gateway, forwards only the approval CSRF header on allowlisted approval routes, and injects a signed browser-session binding.

The default policy registry is empty. Consequently, even an operator setting the approval flag to `true` cannot create a proposal or enable a mutation. There is deliberately no proposal-creation route and no claim/dispatch caller. This foundation does not constitute fresh identity-provider reauthentication, proof that a human inspected the effect, a live upstream ownership check, or authorization to deploy.

Expired sessions and proposals are rejected by their timestamps but this foundation does not automatically purge their rows. Proposal arguments are encrypted with the existing configured D1 encryption key. Before persisting real proposals or adding a reviewed policy, define a retention period and an auditable cleanup mechanism; no production data cleanup was added here.

## Synthetic rehearsal

`examples/operation-approval/demo.html` is a static, browser-only illustration using fixed fake account/condition IDs. `rehearsal.mjs` has no provider, Worker, D1, credential, or dispatch dependency; its in-memory store is intentionally unsuitable for production. The demo asks the user to enable the rehearsal, displays a fixed effect summary, simulates a one-time approval and claim, and can simulate an `outcome_unknown` stop. The approval nonce stays in local page memory and is omitted by the model/tool-safe serializer. The page uses `textContent` for rendered data and makes no outbound API or provider requests; serve the files over loopback for browser module loading.

`scripts/test-operation-approval.mjs` exercises the standalone mock state machine and confirms the real MCP catalog and raw transport still reject write policies before fetch. `scripts/test-operation-approval-ui.mjs` covers interrupted browser-only rehearsal flows. `scripts/test-operation-approval-store.mjs` runs the production approval service against SQLite with the D1 schema, including session owner/CSRF binding, generation drift, encrypted-argument storage, nonce replay/concurrency CAS, single-use claim, and `outcome_unknown`. It also exercises Sites and signed-proxy Worker routes using synthetic identities and a fake backend, with zero provider requests. These tests do not validate ChatGPT Sites cookies in a real browser, a real operator identity adapter, live provider resource ownership, actual New Relic effects/costs, or deployment behavior. The production connection page explicitly states that write and destructive operations are unavailable.

## Required flow before any future mutation support

1. **Build a proposal, not an action.** After authenticating the current owner, resolve the exact tool name, full existing tool fingerprint (input/output schema, annotations and metadata), canonical arguments, New Relic account and region, connection generation, operation class, and known billing class. Reject unknown or changed definitions and unknown billing classifications. Verify ownership of exact resource targets; an account argument alone does not prove ownership of arbitrary GUIDs or organization-level resources. Display exact effects in local UI; never use provider-supplied prose as authority.
2. **Get deliberate owner approval.** Authentication by a Sites identity header or signed-proxy JWT identifies a principal but does not prove human approval. Require a deliberate authenticated `POST` with strict JSON content type and a single-use server nonce bound to the browser session, owner, and immutable proposal. Never expose the nonce through MCP or accept an `approved: true` MCP argument. Bind approval to the same subject, account, region, connection generation, operation, canonical-argument hash, full tool/policy fingerprint, and proposal expiry. Protect the browser flow with strict Origin checks and gateway session CSRF protections. A confirmation in chat is not automatically a server-side approval token.
3. **Claim atomically.** Store an immutable, expiring proposal and perform a conditional `pending -> claimed` transition before dispatch. The claim must succeed once only. Revalidate user, account, connection generation, tool policy, current full tool fingerprint, arguments, billing classification, and feature flags at claim time. Account switch, disconnect, reconnect, or credential-principal change invalidates pending approval.
4. **Dispatch once.** Use only the exact reviewed transport path and exact arguments. If using `withNewRelicSession()`, explicitly pass `{readOnly:false}` because its default can replay a callback after refreshable auth failure. Do not expose a raw-tool escape hatch or retry a mutation after `401`, timeout, disconnect, or ambiguous response. Malformed results, a crash or a failure to persist the result after dispatch are `outcome_unknown`; stop and require an operator to inspect provider state. Do not assume the provider supports idempotency keys. Disconnect can fence stale, not-yet-dispatched work but cannot undo an action already sent upstream.
5. **Record safely.** Record proposal ID, subject/account references, tool name, schema and argument hashes, approval/claim timestamps, result class, and correlation IDs. Avoid retaining raw telemetry, full arguments, OAuth data, or bearer assertions in logs. Render provider text and arguments as text, never HTML.

## Independent safeguards

- Every write/destructive tool is disabled by default and requires an explicit operation-specific policy plus a separate approval feature flag. A billing opt-in is not a write approval.
- The UI must show whether an operation can alter alerts, thresholds, routing, entities, or other production state, and must identify any provider costs or external side effects that are known. Unknown effects block the action.
- Authorization must remain owner-scoped; another user cannot view, approve, replay, or alter the proposal. Tests must cover duplicate clicks, stale approvals, changed arguments/schema/policy, cross-origin requests, account switching, disconnect races, concurrent dispatch, and provider timeouts.
- Before release, obtain independent review and test against a dedicated non-production New Relic account with harmless fixtures. Do not use live production entities as approval-flow test targets.

Before any future mutation policy is added, obtain official tool schemas and effect semantics, implement an authenticated first-party proposal UI, verify ownership of every target, review billing/effects, and test with a dedicated non-production New Relic account. Until then, keep the policy registry empty, the flag off, and the fail-closed write/destructive behavior. This document does not authorize a live call, production configuration, deployment, or release.
